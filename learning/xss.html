Cross-Site Scripting (XSS)

What is XSS?

Cross-site scripting (XSS) happens when a website shows user input on a page without making it safe first. If the input contains HTML or JavaScript, the browser runs it as part of the page.

There are three main types: reflected (the input comes back in the response straight away), stored (the input is saved, for example in a comment, and shown to every visitor) and DOM-based (the page's own JavaScript writes the input into the page).

How does it work?

The attacker puts a script into a comment, a search box or a URL. The website places that text inside its HTML. Every visitor who opens the page now runs the attacker's script in their own browser.

→
Websitesaves it and shows it on the page
→
Victim's browserruns the script

Why is it dangerous?

  • The script runs as if it were part of the trusted website.
  • It can steal session cookies and take over accounts.
  • It can change what the page shows, for example a fake login form.

A simple example

A search page shows: You searched for: INPUT. The server writes the input straight into the HTML. A basic test string from PayloadsAllTheThings is:

<script>alert('XSS')</script>

If the page shows a pop-up box, the browser ran the input as JavaScript. Another common test uses an image that fails to load:

<img src=x onerror=alert('XSS');>

src=x is not a real image, so the browser fires the onerror event and runs the JavaScript inside it. This works even when <script> tags are blocked.

More examples: XSS on our Cheatsheet.

How to identify it during authorised testing

  1. Find every place where your input appears again on the page (search results, profile names, comments).
  2. Enter a harmless unique word first, then check where it appears in the page source.
  3. Check whether characters like < > " ' come back unchanged.
  4. PayloadsAllTheThings suggests alert(document.domain) instead of alert(1) so you know which website the script ran on.

Common mistakes developers make

  • Using innerHTML with user input instead of textContent.
  • Trying to block only the word <script>.
  • Trusting data that was stored in the database earlier.
  • Forgetting that URLs and attributes need encoding too.

How developers can prevent it

  • Encode output: turn < into &lt; and so on, so the browser shows the text instead of running it.
  • In JavaScript, use textContent to insert user text.
  • Add a Content Security Policy (CSP) header to limit which scripts can run.
  • Mark session cookies as HttpOnly so scripts cannot read them.
