Lesson 08

Server-Side Request Forgery (SSRF)

What is SSRF?

Some features ask the server to fetch a URL, for example "import image from URL" or "preview this link".

Server-side request forgery (SSRF) happens when the attacker chooses that URL and makes the server visit places it should not, such as internal systems that are hidden from the internet.

How does it work?

The server is usually inside a private network, so it can reach addresses the attacker cannot reach directly. By sending it a special URL, the attacker uses the server as a messenger into that private network.

Attackersends an internal URL
→
Web serverfetches the URL for them
→
Internal servicereturns private data

Why is it dangerous?

  • Attackers can reach internal admin pages and services.
  • In the cloud, they can read metadata that may contain secret keys.
  • They can scan the internal network through the server.

A simple example

PayloadsAllTheThings shows a server that fetches any URL the user gives it:

url = input("Enter URL:")
response = requests.get(url)
return response

An attacker supplies the address of the cloud metadata service:

http://169.254.169.254/latest/meta-data/

169.254.169.254 is a special address that only works from inside a cloud server (AWS EC2 in this example). The page it returns can include sensitive information about the server.

More examples: SSRF on our Cheatsheet.

How to identify it during authorised testing

  1. Look for features that take a URL: image import, webhooks, PDF generators, link previews.
  2. On an authorised lab, give the feature an address you control and check if the server visits it.
  3. Try http://127.0.0.1 or http://localhost to see if internal pages are reachable.

Common mistakes developers make

  • Fetching any URL the user sends.
  • Using a block list that misses other ways of writing an address (PayloadsAllTheThings lists many, like http://2130706433/ for 127.0.0.1).
  • Following redirects to internal addresses.

How developers can prevent it

  • Only allow a fixed list of trusted domains.
  • Block private and internal IP ranges after the address is resolved.
  • Turn off redirects, and allow only http and https.
  • Protect cloud metadata (for example, AWS IMDSv2).
