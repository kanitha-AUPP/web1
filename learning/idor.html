Lesson 04

Insecure Direct Object References (IDOR)

In this lesson

What is IDOR?

An IDOR is a common type of broken access control. The website uses an ID from the user (in the URL, a form or an API request) to find a record, but it does not check if that record belongs to the user.

Changing the ID, for example from 123 to 124, shows someone else's data.

How does it work?

Records in a database usually have simple numbers as IDs. If the server trusts the ID it receives and never asks "does this record belong to the logged-in user?", any user can request any record.

User 123changes the URL to user_id=124
→
Serverlooks up 124 without checking the owner
→
Responseshows user 124's profile

Why is it dangerous?

  • Private data such as orders, messages and invoices can be read.
  • Sometimes data can also be changed or deleted.
  • Attackers can collect data from every user by counting up the IDs.

A simple example

PayloadsAllTheThings uses this example. A user views their own profile with:

https://example.com/profile?user_id=123

If the server does not check ownership, changing the number shows another user's profile:

https://example.com/profile?user_id=124

The only thing that changed is the ID. A safe website would reply "403 Forbidden" because user 123 does not own profile 124.

More examples: IDOR on our Cheatsheet.

How to identify it during authorised testing

  1. Create two test accounts (A and B) on an authorised lab.
  2. As user A, note the IDs in URLs and requests.
  3. Log in as user B and try to use user A's IDs.
  4. Also try IDs in hidden form fields, cookies and JSON request bodies.

Common mistakes developers make

  • Thinking an ID is safe because the user "cannot see" other IDs.
  • Believing long or encoded IDs are a security control. PayloadsAllTheThings shows how even hashed or time-based IDs can be guessed.
  • Checking ownership when reading data but not when updating or deleting it.

How developers can prevent it

  • Always check that the record belongs to the logged-in user before returning it.
  • Take the user's identity from their session, not from a parameter they can change.
  • Use random, hard-to-guess IDs as an extra layer (not as the only protection).
  • Test every endpoint with two accounts during development.
