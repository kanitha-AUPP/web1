What is Broken Access Control?

Authentication asks "who are you?". Access control (also called authorisation) asks "what are you allowed to do?".

Broken access control means the website does not check permissions properly, so a normal user can see or do things that should be limited to other users or to admins. It is number 1 in the OWASP Top 10 (2021).

How does it work?

Many websites only hide buttons and links from users who should not use them. But the pages and API requests still exist. If the server does not check permissions on every request, anyone who knows (or guesses) the address can use them.

Why is it dangerous?

  • Users can read or change other people's data.
  • Normal users can become admins.
  • Attackers can delete data or change settings for the whole website.

A simple example

The admin link is hidden from normal users, but the page itself is not protected:

https://example.com/admin/users

PayloadsAllTheThings also lists request tricks that sometimes skip permission checks, such as changing the HTTP method or sending the same parameter twice:

POST → PUT
user_id=hacker_id&user_id=victim_id

If the server checks permissions only for POST, a PUT request may get through. If it checks the first user_id but uses the second, the request may act on another user.

More examples: Broken Access Control on our Cheatsheet.

How to identify it during authorised testing

  1. Log in as two test users with different roles and compare what each can reach.
  2. Try opening admin URLs while logged in as a normal user.
  3. Change the HTTP method of a request and see if the result changes.
  4. Check whether actions work after you remove or change cookies.

Common mistakes developers make

  • Hiding a button and assuming that is enough protection.
  • Checking permissions in JavaScript in the browser only.
  • Checking permissions on some pages but forgetting the API.
  • Trusting a role sent by the browser, such as role=admin.

How developers can prevent it

  • Check permissions on the server for every request.
  • Deny by default: only allow what each role really needs.
  • Keep the permission check in one shared place in the code so it is not forgotten.
  • Log access-control failures and alert admins about repeated attempts.
