SQL Injection (SQLi)

What is SQL Injection?

Most websites store their data (users, products, orders) in a database. They talk to the database using a language called SQL.

SQL injection happens when a website puts what the user typed directly into an SQL query. If the input contains SQL characters, the visitor can change the meaning of the query.

How does it work?

A login form sends the username to the server. The server glues it into a query string and sends it to the database. The database cannot tell which part was written by the developer and which part was typed by the user.

Why is it dangerous?

  • Attackers can log in without a password.
  • They can read private data such as emails and password hashes.
  • In some cases they can change or delete data in the database.

A simple example

Imagine a login form. The server builds this query from the two input boxes:

SELECT * FROM users WHERE username = 'INPUT' AND password = 'INPUT';

PayloadsAllTheThings shows what happens when the username is ' OR '1'='1'--. The query becomes:

SELECT * FROM users WHERE username = '' OR '1'='1'--' AND password = '';

The ' closes the username text, OR '1'='1' is always true, and -- turns the rest of the line (the password check) into a comment. The database returns users without checking any password.

More examples: SQL Injection on our Cheatsheet.

How to identify it during authorised testing

  1. Type a single quote ' into a field and look for a database error message.
  2. Compare the page for a true condition (1=1) and a false condition (1=2). Different responses are a strong sign.
  3. Watch for long delays after time-based tests such as SLEEP(5).
  4. Tools like Burp Suite and sqlmap can help, but only on authorised targets.

Common mistakes developers make

  • Building queries by joining strings with user input.
  • Showing full database error messages to visitors.
  • Only checking input with JavaScript in the browser (it can be skipped).
  • Giving the website's database account more permissions than it needs.

How developers can prevent it

  • Use parameterised queries (prepared statements). The input is sent separately from the query, so it can never change the SQL.
  • Validate input on the server (for example, an ID must be a number).
  • Show a general error page instead of database errors.
  • Give the database user only the permissions it needs.
