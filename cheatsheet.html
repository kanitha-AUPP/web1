SQL Injection (SQLi)

A03 Injection

User input is placed into a database query, so the visitor can change what the query does.

Testing concepts: Add an SQL character such as a single quote and watch for errors or changed behaviour. Compare a true condition (1=1) with a false one (1=2).

Examples

Authentication bypass

' OR '1'='1'--

Makes the WHERE condition always true and comments out the password check.

Logic test in a URL

page.asp?id=1' or 1=1 -- true

A classic true/false test to confirm the input reaches the query.

Read data with UNION

1' UNION SELECT username, password FROM users --

Adds a second query that returns usernames and passwords.

Time-based (blind) test

' AND SLEEP(5)

If the page takes about 5 seconds, the input is running inside the query.

Common mistakes

  • Joining user input into query strings
  • Showing database errors to visitors
  • Trusting browser-side validation only

Prevention

  • Use parameterised queries (prepared statements)
  • Validate input types on the server
  • Limit the database account's permissions

Source: PayloadsAllTheThings / SQL Injection (MIT License)

Cross-Site Scripting (XSS)

A03 Injection

User input is shown on a page without encoding, so the browser runs it as HTML or JavaScript.

Testing concepts: Enter a unique word and find where it appears in the page source. Check whether < > " ' come back unchanged, then try a harmless script.

Examples

Basic test

<script>alert('XSS')</script>

If a pop-up appears, the input ran as JavaScript.

Break out of an attribute

"><script>alert('XSS')</script>

The "> closes an existing HTML tag first, then adds a script.

Image error event

<img src=x onerror=alert('XSS');>

Works when <script> is blocked; the broken image fires onerror.

SVG tag

<svg onload=alert(1)//

An HTML5 tag that runs JavaScript when it loads.

Common mistakes

  • Using innerHTML with user input
  • Blocking only the word <script>
  • Trusting data saved earlier in the database

Prevention

  • Encode output for HTML
  • Use textContent in JavaScript
  • Add a Content Security Policy
  • Set cookies as HttpOnly

Source: PayloadsAllTheThings / XSS Injection (MIT License)

Broken Access Control

A01 Broken Access Control

The website does not check permissions properly, so users can reach actions or data meant for others.

Testing concepts: Compare two accounts with different roles. Try admin URLs as a normal user, and change the HTTP method of a request.

Examples

Reach a hidden admin page

https://example.com/admin/users

The link is hidden, but the page itself is not protected on the server.

Change the HTTP method

POST → PUT

A permission check written only for POST may miss a PUT request.

Parameter pollution

user_id=hacker_id&user_id=victim_id

Sending an ID twice can confuse which value the server trusts.

Common mistakes

  • Hiding a button instead of checking on the server
  • Checking permissions in the browser only
  • Protecting pages but not the API

Prevention

  • Check permissions on the server for every request
  • Deny by default
  • Keep the access check in one shared place

Source: PayloadsAllTheThings / Insecure Direct Object References (MIT License)

Insecure Direct Object References (IDOR)

A01 Broken Access Control

The server uses an ID from the user to fetch a record without checking that the record belongs to them.

Testing concepts: Note the IDs your account uses, then log in as a second account and try the first account's IDs in URLs, forms and JSON.

Examples

Change a numeric ID

https://example.com/profile?user_id=124

If ownership is not checked, this shows another user's profile.

Try a wildcard

GET /api/users/* HTTP/1.1

Some weak APIs return every user when sent a wildcard.

ID inside JSON

{"id":[19]}

Wrapping the ID in an array can slip past weak checks (an IDOR tip from the repo).

Common mistakes

  • Thinking an ID is safe because it is hard to see
  • Believing long or hashed IDs cannot be guessed
  • Checking ownership on read but not on delete

Prevention

  • Check record ownership on every request
  • Use the identity from the session, not a parameter
  • Test every endpoint with two accounts

Source: PayloadsAllTheThings / Insecure Direct Object References (MIT License)

Authentication Vulnerabilities

A07 Identification & Authentication Failures

Weak login, registration, password-reset or session handling lets an attacker take over an account.

Testing concepts: Check for a limit on wrong passwords. Request two reset tokens and compare them. See if the old session still works after logout.

Examples

Email parameter pollution

email=victim@mail.com&email=hacker@mail.com

A weak reset may read the first email but send the link to both.

Email list in JSON

{"email":["victim@mail.com","hacker@mail.com"]}

Same idea sent as a JSON array of addresses.

Carbon-copy injection

email=victim@mail.com%0A%0Dcc:hacker@mail.com

Newline characters try to add a CC header so the attacker also gets the email.

Common mistakes

  • Unlimited login attempts
  • Reset tokens that are predictable or never expire
  • Different messages for wrong username vs wrong password

Prevention

  • Rate-limit logins and add MFA
  • Make reset tokens long, random, single-use and short-lived
  • Create a new session after login and end it on logout

Source: PayloadsAllTheThings / Account Takeover (MIT License)

Security Misconfiguration

A05 Security Misconfiguration

The server, framework or cloud service is set up in an unsafe way, for example default passwords or open admin tools.

Testing concepts: Look for admin and debug pages at common addresses. Read error pages and response headers. Test CORS with an evil Origin.

Examples

Find an exposed admin panel

https://example.com/admin

Admin panels on predictable URLs may still use default credentials like admin/admin.

Default credentials

admin / admin

Default logins are public, so they are the first thing attackers try.

CORS trusts any site

Origin: https://evil.com

Access-Control-Allow-Origin: https://evil.com
Access-Control-Allow-Credentials: true

The server reflects the attacker's origin and allows credentials, so evil.com can read private data.

Common mistakes

  • Leaving default passwords in place
  • Debug mode on in production
  • CORS settings that allow every origin

Prevention

  • Change all default passwords
  • Turn off debug mode and hide errors
  • Allow only trusted origins in CORS
  • Remove unused features

Source: PayloadsAllTheThings / Insecure Management Interface (MIT License)

Path Traversal

A01 Broken Access Control

A file name from the user is added to a path, so ../ sequences can read files outside the intended folder.

Testing concepts: Find parameters that look like file names (file=, page=, download=). Try ../ and its encoded versions on an authorised lab.

Examples

Basic traversal

../../../etc/passwd

Steps up three folders, then names a readable Linux system file.

URL-encoded

%2e%2e%2f%2e%2e%2f%2e%2e/etc/passwd

%2e%2e%2f is ../ encoded, to get past filters that block plain ../.

Filter bypass

..././

Becomes ../ again if the filter removes ../ only once.

Common mistakes

  • Joining user input to a path directly
  • Blocking only the exact text ../
  • Running the server with wide file permissions

Prevention

  • Use an allow list of files or IDs, not raw input
  • Allow only letters and numbers in names
  • Check the final path stays inside the allowed folder

Source: PayloadsAllTheThings / Directory Traversal (MIT License)

Server-Side Request Forgery (SSRF)

A10 SSRF

A feature fetches a URL chosen by the user, so the server can be made to visit internal systems.

Testing concepts: Find features that take a URL (image import, webhooks, link preview). On a lab, point them at an address you control, then at localhost.

Examples

Cloud metadata

http://169.254.169.254/latest/meta-data/

A special address reachable only from inside a cloud server; may expose secrets.

Reach localhost

http://127.0.0.1:80

Tests whether the server can be made to call itself and reach internal pages.

Read a local file

file:///etc/passwd

The file:// scheme turns an SSRF into a file read on the server.

Encoded IP bypass

http://2130706433/

A decimal way of writing 127.0.0.1 that can get past a block list.

Common mistakes

  • Fetching any URL the user sends
  • Block lists that miss alternate IP formats
  • Following redirects to internal addresses

Prevention

  • Allow only a fixed list of domains
  • Block private IP ranges after resolving
  • Disable redirects; allow only http and https

Source: PayloadsAllTheThings / Server Side Request Forgery (MIT License)

File Upload Vulnerabilities

A05 Security Misconfiguration

An upload form accepts dangerous files, which the server may then run as code or serve to other users.

Testing concepts: Find every upload form. On a lab, upload a harmless file with different extensions and content types and see which are accepted.

Examples

Double extension

shell.jpg.php

Looks like an image to a weak filter but ends in .php so the server runs it.

Case and null-byte tricks

.pHp
.php%00.jpg

Mixed case or a null byte can confuse a filter that checks the extension.

Fake the content type

Content-Type: image/gif

The request claims the file is an image; a server that trusts this header is fooled.

Common mistakes

  • Checking only the extension or Content-Type
  • Using a block list instead of an allow list
  • Keeping the user's original file name

Prevention

  • Allow only the file types you need
  • Rename every file to a random server name
  • Store uploads outside the web root
  • Limit size and check real content

Source: PayloadsAllTheThings / Upload Insecure Files (MIT License)

Command Injection

A03 Injection

User input is placed into an operating-system command, so special characters let the attacker run their own commands.

Testing concepts: Find features that use system tools (ping, DNS lookup, file convert). On a lab, add a separator and a harmless command, or a time delay.

Examples

Chain a command with ;

8.8.8.8; cat /etc/passwd

The ; ends the ping command and runs cat /etc/passwd after it.

Command separators

command1; command2
command1 && command2
command1 | command2

Different shell characters that join or pipe commands together.

Time-based test

; sleep 5

If the response is about 5 seconds slower, the command ran even with no output shown.

Common mistakes

  • Passing input to system() or exec()
  • Blocking only a few characters
  • Running the web server as administrator

Prevention

  • Avoid system commands; use built-in functions
  • Use an allow list for the input
  • Pass arguments separately, not as one string
  • Run with the lowest permissions

Source: PayloadsAllTheThings / Command Injection (MIT License)
